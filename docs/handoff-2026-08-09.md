### 2-4. 아티팩트 검증 게이트 (`6852146`, `d2375a1`)

3장 장애의 재발 방지책. prod/dev 양쪽에 동일 패턴 적용.

**빌드 잡**: 산출물 생성 직후 `sha256sum ... | tee SHA256SUMS`, `SHA256SUMS`를 아티팩트에 포함
**배포 잡**: 스테이징/복사 **직전** `sha256sum -c SHA256SUMS` + `unzip -t` + `ls -l`

두 겹인 이유 — 체크섬은 전송 중 잘림·변조를, `unzip -t`는 **크기는 맞는데 열리지 않는 파일**을 잡는다. `ls -l`을 남긴 건 다음 사람이 로그만 봐도 크기 이상을 알아채게 하기 위함이다(이번 사고 때 스테이징 목록의 52MB를 보고도 비교 기준이 없어 지나쳤다).

dev는 스테이징 단계가 없어 곧장 라이브를 덮어쓰고 재시작하므로, **첫 `cp` 전에 3개 아티팩트를 일괄 검증**한다. 하나라도 깨졌으면 아무것도 복사되지 않는다(절반만 교체된 상태 방지).

검증 테스트: 정상 war를 사고와 동일한 52,287,189 bytes로 잘라 게이트에 태움 → `sha256sum -c` exit 1, `unzip -t` exit 9. `run` 스텝은 `bash -e`라 잡이 즉시 실패한다.

| 8/9 08:35 | CounselMan·병실현황판 SSO 진입 실패 신고 |
| 8/9 08:42 | 롤백 복구 완료 |

### 증상

- Tomcat 404 (`HTTP 상태 404 – 찾을 수 없음`)
- `csm-next` 로그에 exception 없음 ← **앱이 기동조차 못 했다는 신호**
- CounselMan(`/counsel/list`)과 병실현황판(`/room-board`) **양쪽 모두** 실패 → 공통 경로 문제 시사

### 원인

`/opt/csm-next/tomcat/webapps/csm.war`가 **127,920,134 → 52,287,189 bytes로 잘린 파일**. zip은 파일 끝의 central directory로 목록을 읽는데 그게 없어 Tomcat이 컨텍스트를 explode하지 못했다.

확정 근거:
1. 동일 커밋 로컬 빌드는 정상 — 127,947,448 bytes, 921 엔트리, `unzip -t` 통과
2. 아카이브된 문제 파일 `file` 결과 → `Zip archive data, at least v2.0 to extract` (앞부분은 온전, 뒤가 잘림)
3. 워크플로가 `cp` → `mv`를 완료했으므로 러너가 받은 아티팩트가 **이미 잘려 있었음**
4. 빌드와 스테이징 사이에 있는 건 아티팩트 업로드/다운로드뿐

→ **아티팩트 전송 중 잘림**

### 배제된 가설 (같은 길 다시 가지 말 것)

| 가설 | 반증 |
|------|------|
| 디스크 풀 | `df -h /opt/csm-next` → 61% 사용, 20G 여유 |
| 아티팩트 zip이 그대로 복사됨(이중 압축) | war를 재압축하면 118MB. 52MB와 안 맞음 |
| SSO 서명/시크릿 불일치 | `CounselManSsoLinkService` 6/17 이후 변경 없음. `SERVICES_WITH_ROLE`는 `CANCER_TREATMENT`뿐이라 문제 URL은 4-field 서명 유지 |
| CSM측 SSO 검증 로직 변경 | `MediplatSsoController`·`MediplatSsoService`·`SecurityConfig` 해당 배포에 변경 없음 |
| 링크 만료 | 발급 60초 이내 클릭 |

### 복구 절차 (재발 시 그대로 사용)

```bash
# 1) 디스크 여유 확인 (부족하면 롤백 cp도 잘린다)
df -h /opt/csm-next

# 2) 되돌릴 백업 무결성 확인
sudo unzip -t /opt/csm-next/tomcat/webapps/csm.war.bak-<TS> 2>&1 | tail -3

# 3) 롤백
sudo cp -a /opt/csm-next/tomcat/webapps/csm.war.bak-<TS> /opt/csm-next/tomcat/webapps/csm.war

# 4) explode 디렉터리 정리 후 재시작 (남아 있으면 Tomcat이 갱신을 건너뛴다)
sudo systemctl stop csm-next
sudo rm -rf /opt/csm-next/tomcat/webapps/csm
sudo systemctl start csm-next

# 5) 확인 (외부 도메인은 서버에서 안 나갈 수 있으니 로컬 Apache 경유)
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: csm.sosyge.net" http://127.0.0.1/csm/login
# 기대: 301
```

### 남은 리스크

아티팩트 다운로드가 **146MB에 약 13분** 걸린다. 잘림의 근본 원인일 가능성이 높고 GitHub/회선 문제라 저장소에서 고칠 수 없다. 게이트는 "깨진 걸 감지해 멈추는" 방어이지 "안 깨지게 하는" 해결이 아니다.

- 재발 시 배포가 빨간불로 실패 → **운영 영향 없음**. Actions에서 "Re-run failed jobs"
- 반복되면 아티팩트 경유 제거(러너 직접 빌드 등) 검토 → TODO.md P3에 등록

```
prod 서버
├─ /opt/csm-next/tomcat/webapps/csm.war      ← csm 본체 (unit: csm-next)
├─ /opt/csm-next/app/mediplat.jar            ← mediplat (unit: mediplat-next, port 18082)

├─ /opt/csm-next/deploy/archive/<TS>/        ← 소비된 스테이징 보관 (사후 분석용)
└─ /opt/csm-next/deploy/scripts/deploy-nightly.sh
```

- 환경 오버라이드: `/etc/default/csm-next-deploy` (`STAGING_DIR`, `CSM_SERVICE`, `MEDIPLAT_APP_DIR`, `MEDIPLAT_SERVICE`, `BACKUP_KEEP=5`)

- **스크립트 기본값과 실제 경로가 다르다** — 반드시 `/etc/default/csm-next-deploy`를 먼저 확인할 것. 오버라이드가 없으면 존재하지 않는 기본 경로(`/opt/mediplat/app`)를 보고 `WARN: live dir missing ... skipping`으로 **조용히 건너뛴다**
