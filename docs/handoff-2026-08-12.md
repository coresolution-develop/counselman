## 1. 왜 결제 코드부터 쓰지 않았나

명세서(`~/Downloads/MediPlat_SMS결제연동_개발명세서.md`)대로 지갑·원장·토스 연동을 바로
만들면 **돈이 새거나 잘못 청구되는 구조 위에 결제를 얹게 된다.** 최초 구조 분석에서
확인된 것들:

| 발견 | 결제 도입 시 결과 |
|---|---|
| 과금 우회 경로 `POST /csm/sms/sendSMS` — 세션 확인·이력 기록 **둘 다 없음** | 이 경로로 나간 문자는 차감도 추적도 안 됨 |
| 메시지 타입(SMS/LMS)을 **클라이언트가 결정** | `type=sms` 로 LMS 분량 전송 → 단가 조작 |
| Bizppurio 호출에 **read timeout 없음** | 응답 지연 시 "발송됨/실패" 구분 불가 → 환불 판단 불가 |
| 결과 리포트 매핑이 `refkey.substring(0,4)` 가정에 의존 | 실패 문자 식별 불가 → 환불 자동화 불가 |
| 리포지토리에 **운영 DB 비밀번호·Bizppurio·카카오 시크릿 평문** | 같은 관행으로 토스 라이브 키를 넣으면 즉시 유출 |

Phase 0 은 이 중 **되돌리기 어렵거나 돈과 직결되는 것**을 먼저 막는 작업이었다.
"과금 가능한 발송 시스템"을 만드는 건 Phase 1 이다.

### 합의된 진행 방식

dev 는 단계별 즉시 적용, prod 는 값만 준비해 두었다가 **1회차 재시작에 한 번에 반영**한다
(누락 3개 + 새 값 전부). 그 재시작으로 **구 WAR 가 환경변수만으로 정상 동작하는지 먼저
확인**하고, **신규 WAR 배포는 별도 2회차**로 분리한다 — 환경변수 문제와 코드 문제를
섞지 않기 위해서다.

        CSRF 예외를 걸면 브라우저 방어가 사라진다

## 7. 함정 목록 — 다음 사람이 밟지 말 것

1. **`@Value("${x:기본값}")` 의 기본값은 키가 없을 때만 적용된다.** 키 값이 미해석
   `${ENV}` 면 그대로 예외. mediplat 이 이걸로 크래시 루프에 빠졌다.
2. **Tomcat hot-deploy 는 조용히 실패한다.** `Deployment ... has finished` 가 찍혀도
   Spring 컨텍스트는 죽어 있을 수 있다. 검증 3종은 `scripts/systemd/README.md` 참고.
3. **`Caused by:` 로그 줄에는 타임스탬프가 없다.** 전체 grep 하면 1년 전 오류가 섞인다.
   반드시 `tail` 로 구간을 좁힐 것.
4. **`systemctl is-active` 는 없는 유닛에도 `inactive` 를 반환한다.** 유닛 이름이
   환경마다 다르므로(`mediplat` vs `mediplat-next`) 먼저 `list-units` 로 확인할 것.
5. **`mp_service` 는 운영자가 관리자 화면으로 추가하는 테이블이다.** 코드에서 등록을
   지워도 기존 행은 남는다. 환경마다 DB 를 따로 확인할 것.
6. **문서의 포트 배정을 믿지 말 것.** `ss -lntp` 로 실측할 것.
7. **8084 는 ResvHub 다.** sms 앱을 기동하면 예약 시스템과 충돌한다.
8. dev DB 의 `transmission_history_*` 중 `HSOP_0001`·`hsop_0001`·`core` 는 **테스트 잔재**다.
   prod 실태 판단 근거로 쓰지 말 것.
